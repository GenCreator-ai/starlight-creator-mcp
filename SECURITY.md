# Security model

The MCP client (Claude, Cursor, Antigravity, Codex) is the principal. The substrate trusts it for content. Provider credentials remain outside the MCP tool surface, and subprocesses use argument arrays. Publication requires a signed manifest after confirmation through the trusted client or local CLI; the server does not independently verify human presence.

## Credentials
- Resolution order: environment variable → OS keychain (`@napi-rs/keyring`: Windows Credential Manager, macOS Keychain, Secret Service) → AES-256-GCM file under `~/.creator-mcp/` (headless fallback, key in `vault.key` 0600 or `CREATOR_VAULT_KEY`).
- Keys are sent only to their provider, in headers (never URL query strings). Logs go to stderr and pass through a redactor that knows every vault value plus common key shapes.
- The MCP tool surface has no "set key" tool. Keys enter via `creator-mcp setup` or the client's own config/MCPB `user_config`.

## Network
- Every outbound request goes through `guardedFetch`: http(s) only, host allowlist (provider hosts + `policy.allowHosts`), private/link-local/loopback ranges blocked (including DNS results), redirects re-checked, size and time limits. Provider result URLs are fetched only when returned by a provider for a job we created.
- `import_url` must be on the allowlist; `CREATOR_ALLOW_PRIVATE_HOSTS=1` exists for tests only.
- The optional S3 SDK transport also uses `guardedFetch`; operators must explicitly allow the resolved S3 endpoint host(s), including AWS (no AWS host is trusted by default). A configured bucket fails closed when the optional connector is omitted (`--omit=optional`) or credentials are missing. Upload bodies are buffered; the signed `Content-Length` must match them and `Expect: 100-continue` is disabled, so SigV4 content and checksum signing is preserved without bypassing the guard. Downloads share the configured asset byte budget and verify the SHA-256 key. Browser-direct presigned uploads are bearer capabilities authenticated by SigV4 and require signed Content-Type and SHA-256 checksum headers; the browser is outside the server's outbound network guard.
- Redirects stop after 20 hops and share one deadline through DNS checks, response headers and body consumption (including `json()`/`text()` and streamed reads). Cross-origin GET/HEAD redirects drop all caller headers and credentials; other cross-origin payloads, URL credentials and HTTPS downgrades are denied. Redirect response bodies are cancelled, and pre-cancelled calls never start a fetch. Actual body bytes are capped when `maxBytes` is configured, including chunked responses without a size header. Failed or empty DNS checks deny the request. A request-scoped Undici dispatcher checks connection-time DNS answers and passes only checked addresses to the socket, preventing a second resolution from bypassing the preflight check. Its connections are destroyed when the response finishes, fails or is cancelled; the global dispatcher is unchanged. A returned body owns its deadline and connection until read or cancelled, so callers cancel (`discardBody`) every non-OK body they do not read. Timing out a DNS check bounds the caller's wait but cannot cancel the OS resolver itself. These guards depend on the configured host policy and address classification; they do not attest a provider's trustworthiness or defend against compromised network infrastructure.
- OpenRouter video content URLs must share the configured API origin before Authorization is sent, even if an external host is allowlisted. Same-origin authenticated content remains supported; cross-origin redirects still strip caller headers.
- MuAPI submission retries 429 and 5xx at most three times, cancelling unread error bodies. Retry-After delays up to two seconds are honored; longer delays return a retryable error to the caller without an early retry. Upload/poll throttling is retryable but is not automatically replayed. Existing 5xx submission retries can duplicate provider work after an ambiguous server failure; no provider idempotency guarantee is claimed.
- The optional HTTP transport binds to 127.0.0.1, validates Host/Origin for localhost, and is stateless per request. Allocated Creator contexts close on protocol teardown and failed registration; caller-supplied contexts remain caller-owned. HTTP shutdown closes active instances and the SDK handler. Contexts still access the same configured durable ledger and assets; per-request allocation is not tenant isolation.

## Filesystem
- Writes are confined by `resolveInside()`: no absolute paths, no `..`, no UNC, symlink escape checked. Roots: `~/.creator-mcp`, the configured assets directory, the `init` target. `init` refuses a workspace `.creator-mcp` that is a symbolic link, junction or file before writing anything.
- Local asset and provenance reads/writes resolve existing parent directories before access, including when the destination has not been created. Outward symbolic links/junctions are denied. Temporary writes use unique names and exclusive creation before rename. These path checks are not a race-proof OS sandbox: operators must protect the storage root and its parents from concurrent untrusted filesystem mutation.
- `AssetStore.bytes` copies and verifies local and connector-supplied bytes against the requested SHA-256 before returning, caching or synchronizing them. A digest mismatch throws; corrupt bytes are neither cached nor silently replaced. This verifies content identity, not the truth of provenance metadata or the trustworthiness of a public URL.
- No shell strings. `rclone` is invoked with `execFile` and an argument array.

## Pack data
- Pack manifests, entities, canon, prompt/template/rubric resources, composite tools and pack digests use portable lexical and real-path containment at each read. Files must be regular files and reads are capped at 8 MiB, including growing files. Canon resources expose only declared canon/locked files; rubric resources enforce the requested pack identity. Pack roots and ancestors must remain protected against concurrent untrusted mutation.
- CLI init preflights the full template tree and destination paths before copying, rejects input links and special files, and checks real destination containment before creating directories or files. It preserves existing regular configuration and templates. This is not a transactional filesystem operation.
- Rubric prompt reads apply both lexical and real-path containment at the point of use, including direct `TasteScorer` calls. Outward directory links are denied. This shares the filesystem mutation limitation above.
- Routing intents and canon forbidden patterns use a bounded literal matcher. Supported syntax is case-insensitive ASCII literals, up to 32 `|` alternatives, one optional outer group, optional outer `\b` boundaries, `\s+` gaps between nonempty literals, and a final `\w*` suffix per alternative. Patterns are limited to 512 characters and matched input to 65,536 characters. Other regex syntax is rejected by directory validation and at runtime; packs using arbitrary regular expressions must migrate. The shipped starter routing pattern and canon whitespace-gap tests retain their behavior. No pack pattern is passed to `RegExp`.

## Publishing
- `creator_publication_prepare` computes a canonical payload hash; `creator_publication_approve` requires the human to type the first 8 characters of that hash through an elicitation form (or the `creator-mcp approve` terminal command). The manifest is then HMAC-SHA256 signed with a key that lives in the vault.
- `creator_publish` verifies signature, expiry (≤ 14 days), recomputed hash and asset bytes before sending; channel sends are idempotent by `sha256(payload_hash | channel | adapter)`; a per-adapter hourly limit is enforced locally.
- Numerical claims without an evidence asset are marked `blocked` and surfaced as warnings.
- Confirmation is supplied by the MCP client's elicitation channel or the local CLI. The server authenticates the resulting manifest with HMAC; it does not independently attest that a human supplied the confirmation. A compromised or automated client can return a matching code. Hosts must keep approval entry separate from untrusted agent execution before treating this as an independent human approval boundary.

## Licenses
- A private pack without a license retains only its declared free sections. Excluding canon also removes locked-document and entity-index references from MCP exposure. This is application behavior, not encryption or a tenant security boundary; an operator who already has the pack files can read them directly.
- Polar keys are validated from the user's machine against the public customer-portal endpoint. Offline use is allowed for 14 days after a *successful online* validation of the same key fingerprint; the cache is MAC-signed so editing it does not unlock anything. There are no length or prefix heuristics.
